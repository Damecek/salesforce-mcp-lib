# salesforce-mcp-lib v2 implementation plan

Design: `docs/superpowers/specs/2026-10-28-mcp-v2-design.md` (the "spec"). Section numbers below
refer to it. Contracts C1 (Apex API), C2 (HTTP wire) and C3 (stdio proxy) are frozen; a change
needs parent sign-off and a spec edit first.

## Chunks and ownership

| Chunk | Owner agent | Files it may touch | Starts | Blocks |
| --- | --- | --- | --- | --- |
| A Apex core | Apex agent | `force-app/**`, `examples/**/force-app/**`, `dev/mcp-harness/force-app/**` | now (after spike S0) | C |
| B npm proxy | npm agent | `packages/salesforce-mcp-lib/src/**`, `packages/salesforce-mcp-lib/tests/**`, `packages/salesforce-mcp-lib/package.json` (`scripts` only) | now, parallel to A | C |
| C docs, package, CI | docs agent | `README.md`, `packages/salesforce-mcp-lib/README.md`, `CLAUDE.md`, `docs/architecture.md`, new `docs/mcp-wire-contract-2026-07-28.md`, `examples/**/README.md`, `dev/**/README.md`, `.github/workflows/ci.yml`, `scripts/release-*.sh`, `sfdx-project.json`, `packages/salesforce-mcp-lib/package.json` (`version` only) | after A and B are green | release |

No two chunks touch the same file. `package.json` is split by field: B owns `scripts`, C owns `version`.
Release (package version create, promote, npm publish, tag, push) is the parent's job after C, using
the `release` skill, and needs the user's explicit go for publish and push.

Model guidance for the parent: A needs a standard model at high effort (protocol plus governor
reasoning). B needs a standard model at medium effort. C needs a lightweight or standard model at
low to medium effort.

> **Step 1, delete.** Remove all of `force-app/main/json-rpc/` and every existing class in

> **Step 2, build these classes** (each with `.cls-meta.xml`, `apiVersion` 65.0, `Active`):
> `McpServer`, `McpTool`, `McpToolResult`, `McpToolAnnotations`, `McpContent`, `McpResourceContents`,
> `McpAnnotations`, `McpIcon`, `McpSchema`, `McpResource`, `McpResourceTemplate`, `McpResourceResult`,
> `McpPrompt`, `McpPromptResult`, `McpCompletion`, `McpRequest`, `McpException`,
> `McpConfigurationException`, `McpRuntime`, `McpWire`, `McpUriTemplate`, `McpProtocolException`.
> Signatures are fixed by spec 5.1. Behaviour is fixed by spec 5.2 to 5.4 and 6.1 to 6.8.
>
> Hard rules:
> - Legal Apex only. No lambdas. No method named like a reserved word (`number`, `object`, `type`,
>   `desc`, `default`, `enum`, `array`, `limit`, `sort`). No field sharing a name with a method.
> - No SOQL, DML, callouts, Platform Cache, custom objects, or static mutable state in the framework.
> - Serialize the whole response envelope once with `JSON.serialize(map)`; never pass
>   `suppressApexObjectNulls=true`; builders never insert null values.
> - Keep request ids as `String` or `Long`. Integral `Decimal` ids become `Long`; fractional, boolean,
>   object, array or null ids are `-32600`.
> - All header reads go through one lower-cased map built once per request.
> - Use `Limits.getLimitHeapSize()` and `Limits.getHeapSize()` at runtime; never hardcode a heap size.
> - Internal errors: `System.debug(LoggingLevel.ERROR, ...)` with type, message, stack; the client
>   sees only `"Internal error"`.
>
> **Step 3, tests** (`@IsTest`, one file per area, fixtures as inner classes):
> - `McpRuntimeTest`: every row of spec 6.1 including both 9a/9b paths, 405, 403 with and without
>   allowlist, 413, batch, bad ids (`1.5`, `true`, `null`, Long id `9007199254740991` echoed exactly),
>   202 notification without headers, `-32022` data shape, modern 404 vs legacy 200 for unknown method,
>   capability gates, `Mcp-Name` plain, base64, bad base64, and mismatch, legacy `_meta` version served
>   as legacy, `initialize` returns `2025-11-25` for `2025-06-18` input.
> - `McpServerTest`: discover shape incl. `ttlMs`, `cacheScope`, `resultType`, serverInfo `_meta`;
>   legacy initialize and ping; legacy results have no `resultType`/`ttlMs`/`cacheScope`;
>   `listCache` and `pageSize` validation; JSON escaping of `"`, `\`, newline in messages.
> - `McpToolTest`: list paging and cursor errors; call happy path; schema failures as `isError`;
>   `McpException` as `isError`; generic exception as `-32603` without its message; output validation
>   and `skipOutputValidation`; legacy drops non-object `structuredContent` and non-object
>   `outputSchema` and adds the text fallback; null values inside structured output survive.
> - `McpSchemaTest`: each supported keyword pass and fail; integral Decimal accepted as integer;
>   10-error cap; raw schema walk limits; `x-mcp-header` and non-local `$ref` rejected.
> - `McpResourceTest`: static read; template match, percent-decoding, first-match order, no match;
>   not found `-32602` modern and `-32002` legacy; `cache()` values; URI over 2048 chars; template
>   syntax rejection (`{+x}`, `{a}{b}`).
> - `McpPromptTest`: list, get with each content type, missing required argument, non-string argument.
> - `McpCompletionTest`: prompt and template refs, unknown ref, undeclared argument, 150 values cut to
>   100 with `hasMore` and `total`.
> - `McpContentTest`: wire shape of all five block types, annotations, `_meta`, icons; size guard
>   returns the size error before serialization for a huge text block.
>
> Target ≥ 90% coverage per class, 100% of tests passing. Run with
> `sf apex run test --target-org <scratch alias> --code-coverage --result-format human --wait 20`
> after `sf project deploy start --source-dir force-app --target-org <scratch alias>`.
>
> **Step 4, examples.** Rewrite `examples/minimal`, `examples/e2e-http-endpoint` and
> `dev/mcp-harness` Apex classes to the new API. Deploy them to the scratch org and run one modern
> `server/discover` and one legacy `initialize` through `sf api request rest` to prove the endpoint.
>
> **Report back:** spike S0 findings, test run summary with coverage, list of files, and any spec
> ambiguity you resolved (with the choice you made).

> **Build:**
> 1. New `src/protocol.ts` with pure functions: `classifyLine(line)` (spec 7.1), `buildHeaders(msg,
>    legacyVersion)` (7.2), `encodeHeaderValue(value)` (base64 sentinel rule),
>    `interpretRemote(status, body, requestId)` returning `{kind:'write', line} | {kind:'silent'} |
>    {kind:'local', reason, httpStatus}` (7.3), `localError(id, reason, httpStatus)` (7.3 format).

> 2. `src/mcpBridge.ts`: forward a classified message with the headers from `buildHeaders`, an
>    `AbortSignal`, the request timeout, and the 8 MiB response cap. Keep the 401 re-auth path. Return
>    the `interpretRemote` outcome. Track `legacyVersion` from successful `initialize` responses in a
>    small state object owned by the bridge instance.
> 3. `src/stdio.ts`: replace `readline` with a byte-bounded line splitter (6 MiB); bounded queue (64)
>    and concurrency (`--max-concurrency`, default 4); in-flight map keyed by `JSON.stringify(id)` for
>    duplicate detection and `notifications/cancelled`; write nothing for silent outcomes; on stdin end
>    drain then exit 0.

>    (1000..600000, default 120000) and `--max-concurrency` / `SF_MAX_CONCURRENCY` (1..25, default 4),
>    with the same validation style as existing flags, and list them in the help text.
